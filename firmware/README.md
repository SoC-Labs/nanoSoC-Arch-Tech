# NanoSoC Firmware

Build infrastructure for NanoSoC firmware: shared library targets, helper
functions, toolchain files, and 22+ testcodes. Two parallel build flows:

- **Make** (authoritative) — `make -C testcodes/<name> all_<toolchain>`
- **CMake** (additive, bit-identical) — `cmake --preset <name> && cmake --build ...`

Both flows produce identical hex output for the supported toolchains; CMake
adds IDE integration, parallel builds, and a clean cross-project consumption
story for downstream subsystems.

---

## Quick start

### Prerequisites

- `arm-none-eabi-gcc` (10.x tested) **or** ARM Compiler 6 (`armclang`)
- CMake 3.25+ (presets v6)
- Project environment sourced: `source set_env.sh` from project root

### Build via CMake (from project root)

```bash
cmake --preset gcc-m0-le               # configure
cmake --build build/cmake/gcc-m0-le    # build all testcodes
                                       # → build/cmake/gcc-m0-le/.../<test>.{elf,hex,bin,lst}

# Single test:
cmake --build build/cmake/gcc-m0-le --target hello

# Other presets:
cmake --preset armclang-m0-le          # ARM Compiler 6
cmake --preset gcc-m0plus-le           # Cortex-M0+
cmake --preset gcc-m0-be               # big-endian
```

### Build via Make (legacy / authoritative)

```bash
make -C testcodes/hello all_gcc TOOL_CHAIN=gcc       # one test
make regression SIMULATOR=vcs                        # full regression
```

## The flow at a glance

Three layers, each with clear ownership:

```
┌────────────────────────────────────────────────────────────────────────┐
│ YOUR PROJECT (nanosoc_m0_project, ethernet-subsystem-ahb, etc.)        │
│   CMakeLists.txt                                                       │
│     add_subdirectory(nanosoc_arch_tech/firmware)                       │
│     add_subdirectory(my_firmware)              ◄── your tests          │
│   CMakePresets.json                              (gcc-m0-le, etc.)     │
│   build_soc/firmware/                                                  │
│     ├─ <project>_memmap.cmake                  ◄── your addresses      │
│     └─ <project>_<profile>_memory.ld           ◄── generated by        │
│   my_firmware/                                     nanosoc_gen         │
│     ├─ my_test/CMakeLists.txt                  ◄── your tests          │
│     └─ scripts/<profile>.ld                    ◄── your linker scripts │
└────────────────────────────────────────────────────────────────────────┘
                              consumes ▼
┌────────────────────────────────────────────────────────────────────────┐
│ UPSTREAM PACKAGE (this directory: nanosoc_arch_tech/firmware)          │
│   nanosoc_add_test()                          ◄── the API              │
│   NanoSoCFirmware::cmsis, ::retarget, ::memmap                         │
│   NanoSoC_STARTUP_ASM, _SYSTEM_C, _RETARGET_SOURCES                    │
│   cmake/toolchains/{arm-gcc,armclang,armcc}.cmake                      │
│   software/{cmsis,common,drivers,debug_tester}                         │
└────────────────────────────────────────────────────────────────────────┘
```

**Upstream owns** the build infrastructure, shared sources, and `nanosoc_add_test()`.
It knows nothing about specific projects.

**Your project owns** the address map (via the generator), project-specific
linker scripts, and test source code. Profiles are picked by name; addresses
flow in from your generated `*_memmap.cmake`.

## What gets reused vs what you write

| Concern | Source |
|---|---|
| `arm-none-eabi-gcc` / `armclang` toolchain wiring | Upstream (`cmake/toolchains/`) |
| Cortex-M0 startup assembly + `system.c` | Upstream (`NanoSoC_STARTUP_ASM`, `NanoSoC_SYSTEM_C`) |
| `printf` retarget over UART | Upstream (`NanoSoCFirmware::retarget`) |
| CMSIS headers, CPU defines | Upstream (`NanoSoCFirmware::cmsis`) |
| DMA / GPIO / etc. driver `.c` files | Upstream (`software/drivers/`) |
| Generic linker scripts (`sections.ld`, `lib-nosys.ld`) | Upstream (`software/common/scripts/`) |
| **Memory addresses (RO/RW bases, regions)** | **Your project** (`build_soc/firmware/<project>_memmap.cmake`) |
| **Project linker `.ld`** (for non-default profiles) | **Your project** (`<project>/scripts/`) |
| **Test `.c` source** | **Your project** |
| **`nanosoc_add_test()` invocation per test** | **Your project** |

## Walkthrough — adding a new test in a consumer project

Suppose you're working in `ethernet-subsystem-ahb` and want to add a test
`eth_loopback` that exercises the ethernet MAC.

### Step 1 — write the test source

```c
// ethernet-subsystem-ahb/firmware/eth_loopback/eth_loopback.c
#include "CMSDK_CM0.h"
#include "uart_stdout.h"
#include "ethernet_ss_ahb_memmap.h"   // generated; gives ETHMAC_0_BASE
#include <stdio.h>

int main(void) {
    UartStdOutInit();
    printf("ethmac base = 0x%08x\n", ETHMAC_0_BASE);
    /* ... your test ... */
    UartEndSimulation();
    return 0;
}
```

### Step 2 — write a CMakeLists.txt next to it

```cmake
# ethernet-subsystem-ahb/firmware/eth_loopback/CMakeLists.txt
nanosoc_add_test(eth_loopback
    INCLUDES
        "${CMAKE_SOURCE_DIR}/build_soc/firmware"   # for ethernet_ss_ahb_memmap.h
        "${CMAKE_SOURCE_DIR}/src/sw"               # project headers
)
```

That's it. Defaults: source = `eth_loopback.c` next door, linker profile =
`cmsdk_cm0`, retarget enabled, GCC `-O3 -g`.

### Step 3 — wire it into the project's top-level CMakeLists.txt (one-time per project)

```cmake
# ethernet-subsystem-ahb/CMakeLists.txt
cmake_minimum_required(VERSION 3.25)
project(eth_ss_firmware C ASM)

set(NanoSoC_FIRMWARE_CONFIG_DIR
    "${CMAKE_SOURCE_DIR}/build_soc/firmware"
    CACHE PATH "Where ethernet_ss_ahb_memmap.cmake + generated .ld live")

list(PREPEND NanoSoC_EXTRA_LINKER_SCRIPT_DIRS
    "${CMAKE_SOURCE_DIR}/firmware/scripts")  # for project-specific .ld files

add_subdirectory(nanosoc_arch_tech/firmware)   # imports nanosoc_add_test()
add_subdirectory(firmware/eth_loopback)        # your test
```

### Step 4 — build it

```bash
cmake --preset gcc-m0-le
cmake --build build/cmake/gcc-m0-le --target eth_loopback
# → build/cmake/gcc-m0-le/firmware/eth_loopback/eth_loopback.{elf,hex,bin,lst}
```

You touched **one source file**, **one 5-line CMakeLists.txt**, and a one-time
top-level wiring.

## `nanosoc_add_test()` — the API

```cmake
nanosoc_add_test(<name>
    [SOURCE_DIR <path>]            # base dir for default MAIN_SOURCE
    [MAIN_SOURCE <file>]           # override the main source (default: <SOURCE_DIR>/<name>.c)
    [SOURCES <files>...]           # extra sources, appended after retarget
    [DRIVERS <files>...]           # driver .c (also adds drivers/ to include path)
    [LINKER_PROFILE <name>]        # default: cmsdk_cm0
    [INCLUDES <dirs>...]
    [DEFINES -DFOO=1 ...]
    [NO_RETARGET]                  # disable retarget link (e.g. bootloader)
    [USE_GENERIC]                  # add testcodes/generic/ to include path
    [CC_FLAGS_GCC <flags>]         # extra flags for GCC
    [CC_FLAGS_ARMCLANG <flags>]    # extra flags for armclang
    [HEX_ADJUST_VMA <name>]        # objcopy --adjust-vma key (e.g. bootloader)
    [STACK_SIZE <hex>]             # default: 0x200
    [HEAP_SIZE  <hex>]             # default: 0x1000
)
```

Generates an `.elf`, `.hex` (verilog), `.bin`, and `.lst` next to the executable.
Toolchain (gcc / armclang) is selected by the active CMake preset; the function
applies the right flags automatically.

### Exported path helpers

Use these in `SOURCES` / `INCLUDES` instead of hardcoding upstream paths:

| Variable | Points to |
|---|---|
| `NanoSoC_SOFTWARE_DIR` | `firmware/software/` |
| `NanoSoC_SOFTWARE_COMMON_DIR` | `firmware/software/common/` |
| `NanoSoC_DRIVERS_DIR` | `firmware/software/drivers/` |
| `NanoSoC_DEBUG_TESTER_DIR` | `firmware/software/debug_tester/` |
| `NanoSoC_TESTCODES_GENERIC_DIR` | `firmware/testcodes/generic/` |
| `NanoSoC_CMSDK_DRIVER_C` | `CMSDK_driver.c` for the active CPU variant |

## Variations on the theme

### A. Test using a project-specific linker profile

Your generator emits e.g. `ETH_SS_BOOTLOADER_RO_BASE = 0x08000000` →
`NanoSoC_PROFILE_eth_ss_bootloader_RO_BASE` in `<project>_memmap.cmake`.

```cmake
nanosoc_add_test(eth_bootloader
    LINKER_PROFILE eth_ss_bootloader     # name from your generated memmap
    NO_RETARGET                          # bootloader has no UART
    CC_FLAGS_GCC -Os -flto -mthumb-interwork
)
```

Drop `eth_ss_bootloader.ld` in a dir you added to `NanoSoC_EXTRA_LINKER_SCRIPT_DIRS`
and it's picked up automatically.

### B. Test pulling in an upstream driver

```cmake
nanosoc_add_test(my_dma_test
    DRIVERS "${NanoSoC_DRIVERS_DIR}/dma_pl230_driver.c"
)
```

### C. Test with multiple local source files

```cmake
nanosoc_add_test(my_complex_test
    SOURCES                              # extras, appended after retarget
        "${CMAKE_CURRENT_SOURCE_DIR}/helpers.c"
        "${CMAKE_CURRENT_SOURCE_DIR}/regs.c"
)
```

If your main file isn't `<name>.c` (e.g. dhrystone with `dhry_1.c`):

```cmake
nanosoc_add_test(dhry
    MAIN_SOURCE "${NanoSoC_SOFTWARE_COMMON_DIR}/dhry/dhry_1.c"
    SOURCES     "${NanoSoC_SOFTWARE_COMMON_DIR}/dhry/dhry_2.c"
    DEFINES     -DITERATIONS=200
)
```

### D. Test with project-specific defines

```cmake
nanosoc_add_test(my_param_test
    DEFINES -DNUM_ITERATIONS=1000 -DUSE_FAST_PATH
)
```

### E. Test with a post-build step (e.g. generate a `.sv` ROM)

```cmake
nanosoc_add_test(stage0)
add_custom_command(TARGET stage0 POST_BUILD
    COMMAND Python3::Interpreter
            ${CMAKE_SOURCE_DIR}/scripts/bootrom_gen.py
            -i $<TARGET_FILE_DIR:stage0>/stage0.hex
            -o $<TARGET_FILE_DIR:stage0>/bootrom.sv
)
```

## How a new address-map feature gets injected

### Adding a new region (e.g. a CAN controller at `0x60000000`)

1. **Edit YAML** — add the region to your project's `sys_desc/soc_model.yml`.
2. **Regenerate** — `make -C nanosoc_m0_soc soc_model` (or your equivalent).
3. **Use it** — `#include "<project>_memmap.h"` in the test gives you `CAN_0_BASE`.

No CMake or upstream changes required.

### Adding a new linker profile (e.g. for code in a different memory region)

1. **Edit YAML** — add to `linker_profiles:`.
2. **Regenerate** — generator emits
   `NanoSoC_PROFILE_my_new_profile_{RO_BASE,RW_BASE,LD_FRAGMENT}` into
   `<project>_memmap.cmake`.
3. **Drop a script** at `<project>/scripts/my_new_profile.ld`. It typically just needs:
   ```ld
   INCLUDE "lib-nosys.ld"
   INCLUDE "<project>_my_new_profile_memory.ld"   /* the generated MEMORY block */
   INCLUDE "sections.ld"
   ```
4. **Use it** — `nanosoc_add_test(... LINKER_PROFILE my_new_profile)`.

`nanosoc_add_test` reads profile data dynamically by variable name — no
upstream changes needed for new profiles.

## The five mental rules

1. **Source layout = test layout.** Your test directory holds the `.c` and the
   `CMakeLists.txt`. Defaults assume `<dir>/<name>.c`.
2. **Addresses come from your generated `*_memmap.cmake`.** The `LINKER_PROFILE`
   argument is a key into that file.
3. **Linker scripts are searched consumer-first.** Drop yours under a dir
   you've added to `NanoSoC_EXTRA_LINKER_SCRIPT_DIRS`.
4. **Upstream paths are exposed as `NanoSoC_*` variables.** Use them; don't
   hardcode `nanosoc_arch_tech/firmware/...` paths.
5. **Toolchains via presets.** `cmake --preset gcc-m0-le` (or `armclang-m0-le`).
   Switching toolchain doesn't touch any test CMakeLists.txt.

---

## Anti-patterns to avoid

- **Don't `#include` `.c` files.** Use the header for declarations and list
  the `.c` via `DRIVERS` or `SOURCES`. (See the `dataio_dma230_tests` history
  for what happens when you don't.)
- **Don't hardcode addresses in test source.** Always pull from the generated
  `*_memmap.h` so regenerating the address map changes the build with no
  source edits.
- **Don't put project addresses in upstream.** `nanosoc_arch_tech` is
  project-agnostic. New projects bring their own memmap.
- **Don't fork upstream to add a profile.** Profiles are data, not code.
  Add them to your YAML and regenerate.

## Toolchain support matrix

| Toolchain | Status |
|---|---|
| GCC (`arm-none-eabi-gcc`) | Validated; CMake build bit-identical to Make for all 22 testcodes |
| ARM Compiler 6 (`armclang`, DS-6) | Validated; bit-identical for 18/21 (3 use AC5-legacy flags) |
| ARM Compiler 5 (`armcc`, DS-5) | Wiring exists; **codebase incompatible** (uses `__has_include`, not supported by AC5). Same failure mode in Make. |

## Coexistence with the Make flow

The Make flow remains authoritative until the migration completes. Both flows:

- Read the same generated address-map files (`build_soc/firmware/*.{mk,cmake,h,ld}`).
- Use the same source files (no duplication).
- Honour the same `excluded_tests.txt`.
- Produce bit-identical hex output per toolchain.

There are no breaking changes to the Make flow from adding the CMake flow; you
can use either or both.
